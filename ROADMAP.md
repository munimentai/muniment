### ACP interop, and the retired first-party editor extension (owner ruling 2026-07-29)
- OWNER RULING 2026-07-29 — muniment takes the ACP agent direction. muniment exposes the Agent Client Protocol, so any ACP editor drives the muniment runtime. The completed E2 first-party editor extension is RETIRED. The muniment CLI surface is DEFERRED indefinitely under the same ruling. An ADR records the direction before any ACP code.
- MEASURED 2026-07-29 (planner, web research against the protocol site and the package registries) — the owner's facts hold, and three of them change the shape of the decision. ACP is Apache-2.0 and speaks newline-delimited JSON-RPC 2.0 over stdio. The CLIENT spawns the AGENT as a subprocess, so an ACP editor starts a muniment process rather than connecting to one. Protocol version 1 is stable and negotiates as one integer in `initialize`. The v2 schema draft published 2026-07-20 states that its wire protocol may change incompatibly in any SDK release. The Rust crate `agent-client-protocol` published 2.0.0 on 2026-07-23 with MSRV 1.88.0, and `@agentclientprotocol/sdk` published 1.3.0 on 2026-07-21 with zero runtime dependencies. Both SDKs now live outside the protocol monorepo, in `agentclientprotocol/rust-sdk` and `agentclientprotocol/typescript-sdk`, so a dependency pin names the SDK repository rather than the spec repository.
- CONSTRAINT 2026-07-29 (planner) — ACP inverts two of this repository's ownership rules, so the ADR must answer both. First, the editor spawns the agent, while ADR 0012 makes the per-user runtime service the single owner of runtime state, so the spawned process cannot become a second executor. Second, ACP hands filesystem and terminal capability to the CLIENT: the agent calls `fs/read_text_file`, `fs/write_text_file`, and `terminal/*` back into the editor, and it asks the editor for permission through `session/request_permission` with the four option kinds `allow_once`, `allow_always`, `reject_once`, and `reject_always`. muniment owns filesystem access, tool execution, and the authoritative journal, and `chat_answer_permission` plus the `permission.requested` and `permission.resolved` events are how a native gate resolves. The ADR must state whether a gate answered inside a third-party editor satisfies a muniment grant check, and what the receipt records when it does. The protocol documents cancellation for a pending permission request and documents no timeout.
- SEQUENCED 2026-07-29 — the document splits in two, the way ADR 0020 did. Ownership, session identity, governance, the wire subset, capability negotiation, the version stance, and the dependency pins are more decisions than one reviewable ticket carries. Slice 1 decides who speaks ACP and how an ACP session stays governed, including the composition with ADR 0009, ADR 0011, and ADR 0012, and the disposition of the `editor-extension/` directory. Slice 2 decides the supported v1 method subset, the capability answers for `fs` and `terminal`, the v1-versus-v2-draft stance, the pinned SDK versions, and which editors the release claims. Slice 1 carries the governance statement, because governance is what lets an ACP session exist at all. ADR 0021 is reserved for the open on-device classifier store ADR, so the ACP document takes 0022.
- DONE 2026-07-29 — slice 1 landed as ADR 0022 (MUNIDESK-673). The Muniment ACP adapter is the only component that speaks ACP, and it is a thin `muniment.attach/1` client of the ADR 0012 runtime service. That service keeps sole ownership of sessions, threads, runs, effects, and receipts, so the editor-spawned process never becomes a second executor. An editor answer to `session/request_permission` is an input to a Muniment gate rather than a grant. The adapter enters `THREAT_MODEL.md` as a new local client identity whose claimed name, session ID, and `cwd` carry no authority. Planner review 2026-07-30 confirmed the composition with ADRs 0009, 0011, and 0012, the reserved `editor-extension/` disposition, and the explicit statement that the slice selects no SDK and pins no version.
- DONE 2026-07-30 — slice 2 landed (MUNIDESK-683). ADR 0022 now names the client-to-agent subset (`initialize`, `session/new`, `session/load`, `session/prompt`, the `session/cancel` notification) and the agent-to-client subset (`session/request_permission`, the `session/update` notification), and it lists every excluded v1 method with its reason. The filesystem and terminal client-capability answers are both no, the adapter negotiates the integer `1`, and Muniment does not adopt the v2 draft. The pin is the Rust crate `agent-client-protocol` at exactly `2.0.0` under ADR 0019, and the first release claims Zed and JetBrains IDEs after release validation. Planner check 2026-07-30 against the crates.io index confirmed the pin is real: `agent-client-protocol` 2.0.0 published 2026-07-23, declares `rust_version` 1.88.0, keeps every `unstable_*` feature (including `unstable_protocol_v2`) out of `default`, and pulls `agent-client-protocol-schema` 1.5.0 plus an async-io/async-process/futures/schemars tree.

Every session method fails closed, because ADR 0012's runtime service is still a decided direction rather than a built surface, and ADR 0022 already says an ACP request without an authorized service attach fails closed. The crate follows ADR 0011's companion boundary: it depends on `muniment-attach` rather than on `muniment-core`, the desktop crate, or Tauri. ### The on-device classifier store (owner idea 2026-07-29)
- SUPERSEDED 2026-07-29 — the cloud owns prompt classification at ingress.
  Desktop clients send prompts without classification metadata and run no
  resident classifier.
- DONE 2026-07-30 — the desktop removed the Qwen descriptor, acquisition,
  startup worker, user interface, resident inference, and llama.cpp packaging.
  Parakeet remains unchanged.
- OWNER IDEA 2026-07-29 — a third decision document opens this lane, and it supersedes the cancelled MUNIDESK-643. The owner states the architecture. No surface executes a prompt locally. Every surface classifies the prompt on the device, then sends the prompt together with that classification to the muniment cloud, which routes to the customer's own model providers. Local classification is a pre-flight step, so it is not execution. Any surface that can send a prompt needs the classifier, and mobile can send prompts. Two stores follow. The desktop, the CLI, and the editor extension share one copy owned by the device core service. The mobile app carries its own copy.
- MEASURED 2026-07-29 (planner, repo read) — the ADR builds on machinery that already exists. `app.path().app_data_dir()` joined with `models/<name>/` is today's store root (`src-tauri/src/main.rs:32`). `ResidentModelDescriptor` pins `byte_size` and `sha256`, and `verify_model_artifact` refuses a mismatch (`src-tauri/core/src/llama.rs:90-118`). `NativeInstallLock` takes `install.lock`, staging writes a resumable `.part` file over HTTP `Range`, and `replace_revision` publishes atomically behind the `current`, `previous`, and `rejected` pointers (`src-tauri/core/src/llama/lifecycle.rs`). `checked_initial_url` and `checked_redirect_url` are the split host policy the MUNIDESK-571 incident produced (`src-tauri/core/src/model_acquisition_transport.rs:358-393`). The gap is ownership and cross-surface discovery, not download machinery.
- CONSTRAINT 2026-07-29 (planner) — `test/cli-dependency-boundary.sh` allows `muniment-cli` only `muniment-attach`, serde, uuid, and their support crates, and ADR 0011 forbids a `muniment-core` dependency. The CLI therefore cannot link an inference runtime. Slice 1 must say how the CLI reaches a classification without one. ADR 0012 already names the per-user runtime service as the single owner of runtime state, so the ADR composes with it rather than inventing a second owner.
- NOTED 2026-07-29 (planner) — three published rules stand against a mobile classifier today. harness-spec §12.1 says phones run no local models. §12.2 item 2 says mobile has no resident local classifier, so the routing label is produced server-side. ADR 0007 repeats the prohibition as the reason mobile lives in its own repository. The ADR must name all three and state why a pre-flight classification is a different thing. Amending those documents is owner work that follows the accepted ADR.
- SEQUENCED 2026-07-29 (planner) — the document splits in two, the way ADR 0020 did. Nine decisions across two platforms, two repositories, and two delivery mechanisms is more than one reviewable ticket carries. Slice 1 decides the shared desktop store: location and owner, second-surface discovery, pinning and verification, concurrent cold-start fetch, upgrade and eviction, offline and air-gapped installs, and the fetch host and redirect policy. Slice 2 decides the mobile store: its per-platform location, whether the artifact arrives as a post-install download or an install-time asset pack, and what mobile does before its model arrives.
