# Tests without layout cannot see the fold

Our desktop client carries two automated test layers. A fast unit suite runs the interface inside a DOM emulator that has no layout engine. A nightly job installs the real signed package on a virtual machine, signs in for real, sends a prompt, and captures screenshots. Both layers were green while three separate defects put controls where a user could not reach them.

The first defect painted a signed-out lockup behind a live conversation. The nightly screenshots deliberately exclude rendered conversations, for privacy, so no capture ever showed it. The unit suite asserted that the conversation was present and never asserted that the lockup was absent. The second defect clipped a profile panel so its sign-out button rendered past the bottom of the window. Three unit tests clicked that button happily, because a DOM emulator with no layout engine reports every element as reachable. The third defect grew a first-run screen past the window and pushed its three actions to vertical positions 685 through 717 pixels, below the 640-pixel fold of our own minimum window size. A fourth case was subtler still: a design law wanted a two-pixel rule under the last line of a streaming reply, and the browser painted it on all three line boxes of a three-line reply, because the CSS property we used governs the inline edges only.

We did not add a browser to the merge gate. Our build runner has no browser installed, and the cheapest defects in this class turned out to be statically detectable. So we split the problem. Two source-reading lints now parse each component's markup against its own style rules: one fails when markup references a class that no rule defines, and one keeps every color use inside an allowlist. Those catch the whole class of defect where a name exists on one side only. Then we committed a small probe harness that serves the built bundle against a stubbed native bridge, so a person or an agent can render six fixture states in headless Chromium on demand, and measure computed positions rather than guess them.

The evidence for the split is the arithmetic. At the moment those defects existed, the unit suite passed 661 tests across 40 files and the native core suite passed 640 tests across 52 binaries. Neither number moved when the defects landed, and neither number moved when they were fixed. What found them was rendering and measuring: a panel bottoming out past a 720-pixel window, buttons at 685 pixels below a 640-pixel fold, and one rule painted on three line boxes where the law wanted one.

This does not prove that on-demand rendering catches layout regressions reliably. Nothing gates a merge on it, so it catches what someone thinks to look at. It measures no performance. It does not show that a browser in the merge gate is the wrong call in general, because our reason was narrow and local: no browser on the runner, and a statically detectable majority. A stubbed native bridge is also not the real application, so it only finds defects that survive stubbing.

The transferable part is a question to ask before writing the test. Name the layer that can see the defect class you care about. A suite with no layout engine can tell you a control exists. Only something with a layout engine can tell you a user can reach it.
