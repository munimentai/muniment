# Tests without layout cannot see the fold

Our desktop client carries two automated test layers. A fast unit suite runs the interface inside a DOM emulator that has no layout engine. A nightly job installs the real signed package on a virtual machine, signs in for real, sends a prompt, and captures screenshots. Both layers were green while three separate defects put controls where a user could not reach them.

The first defect painted a signed-out lockup behind a live conversation. The nightly screenshots deliberately exclude rendered conversations, for privacy, so no capture ever showed it. The unit suite asserted that the conversation was present and never asserted that the lockup was absent. The second defect clipped a profile panel so its sign-out button rendered past the bottom of the window. Three unit tests clicked that button happily, because a DOM emulator with no layout engine reports every element as reachable. The third defect grew a first-run screen past the window and pushed its three actions to vertical positions 685 through 717 pixels, below the 640-pixel fold of our own minimum window size. A fourth case was subtler still: a design law wanted a two-pixel rule under the last line of a streaming reply, and the browser painted it on all three line boxes of a three-line reply, because the CSS property we used governs the inline edges only.

We did not add a browser to the merge gate. Our build runner has no browser installed, so we split the available checks. One source-reading lint is a narrow guard against markup that references a class with no matching rule. A separate color allowlist enforces the palette, but it detects none of these layout defects. The probe harness serves the built bundle against a stubbed native bridge. It exposes the three layout cases through six fixture states that a person or an agent can render and measure in headless Chromium.

The evidence for the split is the arithmetic. When those defects existed, the unit suite passed 661 tests across 40 files. The native core suite passed 640 tests across 52 binaries. Those green totals did not expose any defect. Rendering and measurement found a panel past a 720-pixel window, buttons below a 640-pixel fold, and one rule on three line boxes. The onboarding overflow remains open because its container still lacks the selected scrolling layout.

This does not prove that on-demand rendering catches layout regressions reliably. Nothing gates a merge on it, so it catches what someone thinks to look at. It measures no performance. It does not show that a browser in the merge gate is the wrong call in general. Our reason was narrow and local: the runner has no browser, and the probe remains an on-demand tool. A stubbed native bridge is also not the real application, so it only finds defects that survive stubbing.

The transferable part is a question to ask before writing the test. Name the layer that can see the defect class you care about. A suite with no layout engine can tell you a control exists. Only something with a layout engine can tell you a user can reach it.
